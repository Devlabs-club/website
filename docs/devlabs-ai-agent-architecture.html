DevLabs AI Agent Architecture

Builder & Founder portals — implementation reference
Generated: June 4, 2026

Short answer: one agent or two?

Two separate agents, not one shared agent. They share infrastructure (OpenRouter, actions API, Supermemory, MongoDB) but have different system prompts, tools, and behavior.

AgentAPI actionPersona
Builder Agentbuilder_chatProfile intelligence — fix proof, imports, availability
Founder Agentfounder_chatHiring — role briefs, search, shortlist, intros

There is also a legacy founder parser in founderAgent.ts (parseFounderAgentTurn) that is not wired to the UI anymore; the live founder flow uses founder_chat only.

Architecture (high level)

UI Layer BuilderAgentTab / BuilderOSDashboard → builder_chat FounderRoleIntakeChat / Onboarding → founder_chat Other dashboards (intros, trials…) → 40+ discrete actions ↓ POST /api/agent/actions (src/pages/api/agent/actions.ts) ↓ actionsHandler.postAgentAction (src/lib/agent/actionsHandler.ts) ↓ builder_chat / founder_chat → generateOpenRouterAgentTurn (tool loop) other actions → generateOpenRouterReply or deterministic code ↓ OpenRouter API (src/lib/openrouter.ts) ↓ MongoDB + optional Supermemory (src/lib/talent/supermemory.ts)

Entry point: All agent traffic is POST /api/agent/actions with body { action, payload }, authenticated via JWT cookie/header. May proxy to a Node backend when shouldUseApiProxy is set.

LLM layer (src/lib/openrouter.ts)

Two call styles

  1. generateOpenRouterReply — single turn, no tools (legacy parse, Devpost scrape, getAgentMessage).
  2. generateOpenRouterAgentTurn — OpenAI-style tool calling (tools, tool_choice: auto).

Builder agent (builder_chat)

Where it is used

  • BuilderOSDashboard.tsx — handleAgentSend → builder_chat (+ resume upload → chat again)
  • BuilderAgentTab.tsx — Profile Agent tab via BuilderDashboardContext
  • BuilderHomeTab.tsx — nudges user toward agent tab

Request payload

{
  "action": "builder_chat",
  "payload": {
    "message": "user text",
    "history": [{ "role": "user" | "assistant", "content": "..." }]
  }
}

Agentic loop

  • Calls generateOpenRouterAgentTurn with tools
  • MAX_ITERATIONS = 5
  • temperature: 0.3, maxTokens: 600
  • Tools executed in parallel per turn; results appended as role: tool messages

Founder agent (founder_chat)

Where it is used

  • FounderRoleIntakeChat.tsx — main chat; sends synthetic __init__ on first load
  • FounderOnboardingChat.tsx — wrapper around FounderRoleIntakeChat
  • FounderOSDashboard.tsx — embeds intake when no roles / editing

Non-chat founder UI still calls /api/agent/actions with actions like run_builder_search, request_intro, generate_trial_project, etc.

Request payload

{
  "action": "founder_chat",
  "payload": {
    "message": "user text or __init__ synthetic",
    "opportunityId": "optional Mongo id",
    "history": [ /* last ~16 turns */ ]
  }
}

Server loads current opportunity (by opportunityId or latest draft), founder startup context, and Supermemory founder profile.

Legacy founder parser (not live chat)

src/lib/talent/founderAgent.ts defines parseFounderAgentTurn: one-shot JSON extraction (intent, message, extractedData). Not imported by UI. Only buildFounderUiBlocks is used from that module in actionsHandler.

Agent vs actions API

postAgentAction is a large RPC router (~30+ actions). Only two are full agentic tool loops: builder_chat and founder_chat.

ConversationalShell.tsx is an older demo UI calling discrete actions, not *_chat.

Other LLM touchpoints (not full agents)

  • Devpost import inside scrapeAndImportProject — extract JSON from markdown
  • getAgentMessage — polished copy after successful mutations
  • founderTrialProject.ts — generate trial project copy
  • roleBriefFieldEnhance.ts — enhance a single brief field
  • routeProjectCrudWithLLM — defined but not called (dead path)

Auth and data flow

  1. JWT from cookie/Authorization → resolveAuthedBuilder or resolveAuthedFounder
  2. Tools read/write Mongo models (BuilderProfile, Opportunity, Shortlist, MatchRecord, …)
  3. Client refreshes local state from response (builder, opportunity, uiBlocks)

Mental model

  • Two conversational agents (builder vs founder), each with its own prompt and tools.
  • One gateway (/api/agent/actions) for chat and non-chat operations.
  • OpenRouter is the only LLM provider for agents; model is env-driven.
  • Supermemory is optional long-term memory.
  • Not a single shared agent class — different tools and semantics by role.
